# Конвенції гілок і комітів

Відповідальна: @tyshchenkooleksandra-hue

## Гілки

| Шаблон | Для чого | Приклад |
|---|---|---|
| `feature/<ім'я>-<тема>` | нова функціональність або розділ довідника | `feature/oleksandra-branching` |
| `fix/<ім'я>-<тема>` | виправлення помилки | `fix/alexandra-gitignore-binaries` |

- Гілка створюється від **свіжого** `main`: `git switch main && git pull && git switch -c feature/…`.
- Ім'я — латиницею, у нижньому регістрі, слова через дефіс: його друкують у терміналі й URL.
- Одна гілка — одна тема — один pull request. Після злиття гілка видаляється автоматично.

## Повідомлення комітів

Формат [Conventional Commits](https://www.conventionalcommits.org/):

```text
<тип>(<область>)?: <опис>

<тіло: чому, а не що — необов'язково>
```

| Тип | Коли |
|---|---|
| `feat` | нова можливість (новий розділ, новий параметр утиліти) |
| `fix` | виправлення помилки |
| `docs` | лише документація |
| `refactor` | зміна структури без зміни поведінки |
| `test`, `ci`, `build`, `chore`, `style`, `perf`, `revert` | тести, конвеєр, збірка, службове, форматування, швидкодія, відкат |

Опис — що робить коміт, **з малої літери**, коротко (до 100 символів), без крапки в кінці. Мова — українська.

| ✅ Правильно | ❌ Неправильно | Чому погано |
|---|---|---|
| `docs: чек-лист рецензування для консольних утиліт` | `update docs` | немає типу; «update» нічого не каже |
| `fix(gitignore): ігнорувати архіви й теку bin/` | `fix` | опису немає зовсім |
| `feat(hook): перевірка формату повідомлення коміту` | `Feat: Hook` | тип із великої літери, опис не пояснює зміну |
| `docs: додати розділ про хук` | `docs: Додати розділ про хук.` | опис з великої літери й крапка в кінці |
| `docs: як забрати довідник у свій репозиторій` | `wip`, `try again`, `fix2` | робочі коміти — не історія |

## Що робити з робочими комітами перед злиттям

У гілці можна комітити як завгодно часто — `wip`, `fix`, `try again` допустимі **поки PR не злитий**.
В історію `main` вони не потрапляють:

- репозиторій дозволяє лише **squash merge**: усі коміти гілки стають одним, його повідомлення —
  заголовок PR. Тому заголовок PR пишемо у форматі Conventional Commits;
- якщо потрібна послідовність осмислених комітів, локально до відкриття PR:
  `git rebase -i main` і позначити робочі коміти як `fixup`.

**Після початку рецензії історію гілки не переписуємо.** Правки за зауваженнями — окремим комітом:
рецензент бачить, що саме змінилося з моменту його коментаря, а `force-push` зламав би посилання
в обговоренні.

## Хук `commit-msg`

[`.githooks/commit-msg`](../.githooks/commit-msg) відхиляє коміт, якщо повідомлення не у форматі вище.

Повідомлення, які Git генерує сам, хук **пропускає**: `Merge …` (`git merge`), `Revert "…"`
(`git revert`), `fixup! …` / `squash! …` / `amend! …` (`git commit --fixup` для `rebase -i --autosquash`).
Інакше хук зупиняв би звичайні операції, і люди почали б обходити його через `--no-verify`.
В історію `main` такі повідомлення однаково не потрапляють — там лише заголовок PR після squash.

### Встановлення

Тека `.git/hooks` **не версіонується** — хук, покладений туди, з клоном не приїде. Тому хук лежить
у версіонованій теці `.githooks/`, а Git'у один раз кажемо, звідки брати хуки:

```bash
git config core.hooksPath .githooks
```

Команду треба виконати **в кожному новому клоні** — це налаштування локальне, у `.git/config`.
На Linux/macOS також: `chmod +x .githooks/commit-msg` (у репозиторії файл уже збережено як виконуваний).

### Перевірка

```text
$ git commit --allow-empty -m "update"
✗ Повідомлення коміту не відповідає Conventional Commits:
    update
$ git commit --allow-empty -m "docs: перевірка хука"
[feature/… 1a2b3c4] docs: перевірка хука
$ git merge main                      # автоматичне «Merge branch 'main' into …» — пропущено
```

Локальний хук можна обійти (`git commit --no-verify`) — він лише економить час автора.
Обов'язкову перевірку той самий формат проходить у CI (див. розділ «Автоматична перевірка»).

## Автоматична перевірка

Локальний хук можна обійти (`--no-verify`) або забути встановити. Тому той самий формат перевіряє
CI — [`.github/workflows/commit-conventions.yml`](../.github/workflows/commit-conventions.yml):

| Що | Коли | Як |
|---|---|---|
| Заголовок PR | при відкритті, редагуванні й кожному пуші в PR | [`action-semantic-pull-request`](https://github.com/amannn/action-semantic-pull-request): тип зі списку вище, опис з малої літери |

**Чому заголовок PR, а не кожен коміт.** Репозиторій зливає лише squash: у `main` потрапляє рівно
один коміт, і його повідомлення — заголовок PR. Робочі коміти гілки (`wip`, `fix` до рецензії)
в історію не потрапляють, тому перевіряти їх у CI немає сенсу.

**Чому це не «на совісті автора».** Перевірка `pr-title` — **обов'язкова** в ruleset
(`required_status_checks`): поки вона червона, кнопка злиття неактивна, і обійти її не може навіть
адміністратор (bypass list порожній).

```text
Заголовок PR «Update stuff»:
  ✗ pr-title — No release type found in pull request title "Update stuff".
Заголовок PR «ci: перевірка заголовка PR і генерація списку змін»:
  ✓ pr-title
```

Хук і CI застосовують **одне правило** (тип зі списку, опис з малої літери), щоб коміт, який пройшов
хук локально, не падав потім у CI.

## Список змін

Генерується з історії `main` інструментом [git-cliff](https://git-cliff.org) за
[`cliff.toml`](../cliff.toml): коміти групуються за типом («Нове», «Виправлення», «Документація»…),
коміти не у форматі Conventional Commits (наприклад, `Initial commit`) відкидаються.

- **Автоматично:** після кожного злиття в `main` workflow `commit-conventions` формує `CHANGELOG.md`
  і показує його в підсумку запуску (Actions → запуск → Summary), файл — в артефакті `changelog`.
  У `main` файл не комітиться: ruleset забороняє зміни без PR і для ботів.
- **Локально:** `git cliff -o CHANGELOG.md` (або `npx git-cliff -o CHANGELOG.md`).

Тому формат важливий не лише для читабельності `git log`: тип коміту визначає, у який розділ списку
змін потрапить зміна.

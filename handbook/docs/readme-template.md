# Шаблон README для консольної утиліти

Відповідальна: @tyshchenkooleksandra-hue

Заготовка для README утиліт, які ми писатимемо в наступних лабораторних. Розділи позначені:
**обов'язковий** — без нього README непридатний, **за потреби** — якщо утиліта це має.

## Шаблон

````markdown
# <назва>

<Одне речення: що робить утиліта і для кого.>

## Вимоги

- ОС: <Linux / macOS / Windows>
- Залежності: <інтерпретатор і версія, зовнішні програми>

## Встановлення

```bash
<команда>
```

## Запуск

```text
<назва> [ПАРАМЕТРИ] <АРГУМЕНТ>...
```

## Параметри

| Параметр | За замовчуванням | Опис |
|---|---|---|
| `-h`, `--help` | — | довідка й вихід |
| `-V`, `--version` | — | версія й вихід |

## Вхід і вихід

- `stdin`: <що читає, чи можна передати через `|`>
- `stdout`: <результат — формат>
- `stderr`: <повідомлення про помилки й діагностика>

## Змінні оточення

| Змінна | Вплив |
|---|---|

## Файли

<Конфігураційні файли, які утиліта читає, і порядок пошуку.>

## Коди виходу

<!-- Перелічити ВСІ коди, які повертає утиліта. Недокументований код = код, на який не можна спиратися в скриптах. -->

| Код | Значення |
|---|---|
| `0` | успіх |
| `1` | <…> |

## Приклад

```text
$ <команда>
<реальний вивід>
```

## Обмеження

<Чого утиліта не вміє; відомі проблеми.>

## Версія

<Поточна версія; з якої версії змінився формат виводу або коди виходу.>
````

## Навіщо кожен розділ

| Розділ | Статус | Чому |
|---|---|---|
| Призначення | обов'язковий | читач за одне речення вирішує, чи це те, що йому треба |
| Вимоги | обов'язковий | «не запускається» найчастіше означає не ту версію інтерпретатора |
| Встановлення, Запуск | обов'язковий | копіюється й виконується без здогадок; синопсис у форматі `man` |
| Параметри | обов'язковий | має збігатися з `--help` — це пункт чек-листа рецензування |
| **Вхід і вихід** | обов'язковий | консольні утиліти з'єднують у конвеєри: треба знати, що йде в `stdout`, а що в `stderr` |
| **Змінні оточення** | за потреби | поведінка змінюється без жодного параметра в команді — найважче для налагодження |
| **Файли** | за потреби | конфіг у домашній теці теж змінює поведінку непомітно |
| Коди виходу | обов'язковий | скрипти й CI реагують на код, а не на текст повідомлення. **Власна утиліта документує всі свої коди**; скорочений перелік — лише для чужих утиліт із посиланням на повний |
| Приклад виводу | обов'язковий | показує формат точніше за опис; має збігатися з реальним виводом |
| Обмеження | обов'язковий | чесно називає, де утиліта не допоможе |
| **Версія** | обов'язковий | приклад виводу й коди виходу залежать від версії |

Розділи, виділені жирним, **не входили** в мінімальний перелік із завдання — їх знайдено під час
перевірки шаблону на реальній утиліті (нижче).

## Перевірка: README для `curl` за цим шаблоном

Мінімальний перелік із завдання: призначення, вимоги, запуск, параметри, коди виходу, приклад,
обмеження. Щоб знайти, чого бракує, порівняла його з розділами `curl --manual` (це `man curl`):

```text
NAME  SYNOPSIS  DESCRIPTION  GLOBBING  VARIABLES  OUTPUT  PROTOCOLS  PROGRESS METER
VERSION  OPTIONS  FILES  ENVIRONMENT  PROXY PROTOCOL PREFIXES  EXIT CODES  BUGS  SEE ALSO
```

| Розділ `man curl` | Чого бракувало в мінімальному шаблоні | Що додано |
|---|---|---|
| `OUTPUT`, `PROGRESS METER` | куди йде результат, а куди індикатор прогресу (`stderr`!) | «Вхід і вихід» |
| `ENVIRONMENT` | `http_proxy`, `CURL_HOME` змінюють поведінку без параметрів | «Змінні оточення» |
| `FILES` | `~/.curlrc` підхоплюється автоматично | «Файли» |
| `VERSION` | коди й вивід залежать від версії | «Версія» |
| `BUGS` | — | уже покрито «Обмеженнями» |

### Приклад заповненого README (скорочено)

````markdown
# curl

Передає дані за URL: завантаження, HTTP-запити до API, перевірка доступності сервісу.

## Вимоги

- Linux, macOS, Windows 10+ (вбудований). Перевірено на curl 8.19.0.

## Запуск

```text
curl [ПАРАМЕТРИ] <URL>...
```

## Параметри

| Параметр | За замовчуванням | Опис |
|---|---|---|
| `-o <файл>` | `stdout` | записати відповідь у файл |
| `-s` | вимкнено | без індикатора прогресу й повідомлень |
| `-S` | вимкнено | разом із `-s`: усе ж показати помилку |
| `-f` | вимкнено | HTTP-код ≥ 400 — помилка (код виходу 22), тіло не виводиться |
| `--max-time <с>` | без обмеження | загальний тайм-аут |

## Вхід і вихід

- `stdout`: тіло відповіді (або нічого з `-o`)
- `stderr`: індикатор прогресу й повідомлення `curl: (<код>) <текст>`

## Змінні оточення

| Змінна | Вплив |
|---|---|
| `http_proxy`, `https_proxy` | запити йдуть через проксі |
| `CURL_HOME` | де шукати `.curlrc` |

## Файли

`~/.curlrc` (`%APPDATA%\_curlrc` на Windows) — параметри за замовчуванням для кожного запуску.

## Коди виходу (найчастіші; повний перелік — `man curl`, розділ EXIT CODES)

| Код | Значення |
|---|---|
| `0` | успіх |
| `6` | не вдалося визначити адресу хоста (DNS) |
| `22` | HTTP-помилка ≥ 400 при `-f` |
| `28` | тайм-аут |

## Приклад

```text
$ curl -sS -o /dev/null -w '%{http_code}\n' https://example.com
200
$ curl -sS https://no-such-host.invalid ; echo $?
curl: (6) Could not resolve host: no-such-host.invalid
6
$ curl -sSf -o /dev/null https://httpbin.org/status/404 ; echo $?
curl: (22) The requested URL returned error: 404
22
```

## Обмеження

Без `-f` HTTP 404/500 вважається **успіхом** (код 0) — у скриптах перевірки доступності `-f` обов'язковий.
````

Висновок перевірки: найважливіша знахідка — розділ «Вхід і вихід». Без `-f` і без знання, що
прогрес іде в `stderr`, скрипт на `curl` «працює» й повертає 0 навіть тоді, коли сервіс лежить.
